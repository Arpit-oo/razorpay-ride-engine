     Context

     Greenfield (C:\code\razorpay has only notes.md, ps.md). Build in-memory
     ride-sharing engine in pure Python + pytest, no DB, no 3rd-party libs.
     Rules from notes.md bind every phase: SOLID small classes, lock-per-item
     (no global lock, no lock during slow work), injectable clock, no
     randomness, one-line comment above each code block, caller-authorization on
     every op, no sensitive data leaks, edge tests (at limit + one past), one
     concurrency test per shared-data phase. Stop for Arpit's OK after each
     phase with 4-point report.

     Decisions (confirmed)

     - Geo: integer 2D grid, Manhattan distance.
     - Scope includes ETA prediction + payment failure handling (from ps.md).
     - Cancel: customer may cancel any time before completion, always free.
     - Surge: int basis points, 10000 (1.0x) .. 30000 (3.0x).
     - Reject: rejecting driver excluded for that ride; re-offer to next-ranked;
       none left -> NO_DRIVER_FOUND.
     - Pool capacity: set per driver from vehicle seats.
     - Rating: int 1–5, by that ride's customer, after COMPLETED, once.
     - Payment: injectable fake gateway, N retries with idempotency key, then
       PAYMENT_FAILED; payment status separate from ride status.
     - Money: int paise, INR.

     Modules (13 files -> 6)

     engine/
       core.py      # Clock, FixedClock, Point, manhattan(), errors, id 
     generator
       models.py    # Driver, Customer, Ride state machine, DriverStats, Caller
       registry.py  # DriverRegistry, RideRegistry — lock per item
       matching.py  # DriverRanker (nearest = proximity-only weights), 
     RoutePlanner, PoolMatcher
       pricing.py   # FareCalculator, DemandTracker, DemandForecaster, 
     SurgeCalculator, EtaPredictor
       rides.py     # RideService (flow + auth), PaymentGateway protocol, 
     PaymentService
     tests/  unit/  integration/  stress/
     Classes stay small/single-job; only file count shrinks.

     Phases (12 -> 6)

     P1 — Foundation (core.py, models.py)
     Clock, Point/manhattan, safe error hierarchy, deterministic ids. Driver
     (location, status, seats), Customer, Caller role checks, Ride state machine
     as pure transitions (no locks yet). __repr__ hides sensitive fields.
     Tests: distance edges, every legal/illegal transition, wrong-role rejects,
     repr leak.

     P2 — Registry + matching/ranking (registry.py, matching.py ranker part)
     Per-driver / per-ride locks; atomic try_claim(driver) compare-and-set
     (AVAILABLE -> RESERVED). DriverRanker: int score from proximity, avg
     rating, completion/acceptance rate; tie-break by id; max radius. Plain
     nearest = same ranker with proximity-only weights (one code path, no
     conflict).
     Tests: radius exact/+1, ties, new-driver default score, concurrency: many
     threads claim same driver -> exactly one wins; location updates no lost
     writes.

     P3 — Pricing + ETA (pricing.py)
     Fare = base + per-cell × distance, min fare. Demand/supply per zone over
     clock-based window; time-of-day buckets; forecast = deterministic moving
     average of past windows; surge clamped bps. ETA = distance × zone traffic
     factor(time bucket) × driver speed factor. Quote carries price + ETA +
     expiry.
     Tests: cap 30000/30001, floor 10000, window & bucket boundaries, min-fare
     boundary, concurrent tracker updates.

     P4 — Ride lifecycle + payments (rides.py)
     request (quote, rank, offer) -> accept / reject (re-offer) / offer-timeout
     -> start -> complete -> pay -> rate; cancel free anytime before complete.
     Payment: idempotency key, bounded retries, gateway called outside all
     locks.
     Tests: double-accept race, cancel-vs-accept race, reject chain to
     NO_DRIVER_FOUND, one active ride per customer, pay success on retry N /
     fail at N+1, concurrent pay charges once, rating once & 1–5 edges.

     P5 — Pooling (matching.py pool part)
     RoutePlanner: permutations with pickup-before-drop, min total distance,
     deterministic tie-break. PoolMatcher: join if seats left and every rider's
     detour ≤ limit; replan on cancel.
     Tests: seats exact/+1, detour exact/+1, order constraint, concurrent joins
     never exceed seats, cancel mid-pool replans.

     P6 — Integration + stress + mutation
     E2E flows (solo, pool, reject chain, cancel, payment failure, ranking shift
     after ratings). Stress tests marked slow with deadlock timeouts. Manual
     mutation pass (flip bounds/comparisons, confirm tests fail).

     Weaknesses found (and fix baked in above)

     1. Nearest vs recommendation conflict — v1 had two matchers, unclear which
        books. Fix: one ranker, nearest = proximity-only weights.
     2. Stale snapshot race — driver picked as available, then taken by another
        ride. Fix: atomic try_claim under driver lock; fall to next candidate on
        failure.
     3. Deadlock risk in pooling — one driver, many ride locks. v1 rule "ride
        then driver" insufficient. Fix: global lock order = driver lock first,
        then ride locks sorted by id; never nested otherwise.
     4. Stuck OFFERED ride — driver never responds. Fix: offer expiry via clock,
        checked lazily on next op -> treated as reject.
     5. Price drift — surge changes between quote and booking. Fix: quote locks
        price, has expiry; expired quote rejected.
     6. Customer double booking — two concurrent requests. Fix: one active ride
        per customer, enforced under customer lock.
     7. Driver goes OFFLINE mid-ride — Fix: only allowed when no active ride.
     8. Pool permutation blow-up — driver-set seats unbounded; 6 riders = 12
        stops = huge factorial. Needs seat cap (see open Q).
     9. Pool fare split undefined — shared ride price per rider not specified
        (see open Q).
     10. Payment "charged but reply lost" — retry could double charge. Fix:
         idempotency key per ride; gateway dedupes.
     11. Free cancel abuse — unlimited cancels cost nothing; unchanged per your
         decision, only noted.
     12. ETA "route optimization" is thin on a Manhattan grid — shortest path is
         trivial; value comes only from traffic factors. Honest limitation.
     13. "Predicted demand" is just moving average — deterministic and simple,
         not ML. Honest limitation.
     14. Mutation testing without libraries — only manual; less rigorous than
         mutmut.
     15. Bigger phases vs "reviewable in 2-3 min" rule — merging to 6 phases
         makes P2 and P4 heavier. Mitigation: I can split P4 (lifecycle /
         payments) if review runs long.

     Open (ask at the phase that needs it)

     - P3: base fare, per-cell rate, min fare, surge weights, time buckets,
       offer/quote expiry seconds.
     - P5: max seats cap, max detour %, pooled fare split rule.

     Verification

     - Each phase: python -m pytest tests -m "not slow" -q; report test count
       before -> after.
     - Final: python -m pytest tests -q incl. stress; manual mutation pass.

  Weaknesses I found, with the fix now in the plan
  1. Two matchers: nearest-driver and recommendation both picked drivers, so it
     was unclear which one booked the ride. Now there's one ranker, and
     "nearest" is that ranker using proximity only.
  2. Stale driver pick: a driver could look free, then get taken by another ride
     before the offer lands. A driver is now claimed in one locked step, and if
     that fails the next driver is tried.
  3. Deadlock in pooling: one driver can hold several rides, so my old "ride
     lock, then driver lock" rule wasn't enough. New rule: driver lock first,
     then ride locks in id order.
  4. Stuck offers: a driver who never replies left the ride waiting forever.
     Offers now expire by the clock and count as a reject.
  5. Price drift: surge could change between the quote and the booking. The
     quote now fixes the price and expires.
  6. Double booking: a customer can have only one active ride at a time.
  7. Driver going offline mid-ride: blocked.
  8. Double charge: a payment could go through but the reply get lost, so a
     retry would charge again. Each ride gets one payment key, so a retry can't
     charge twice.

  Weaknesses I noted but didn't fix
  - Pool route search is unlimited: it tries every stop order, so with no seat
    cap it gets very slow (6 riders = 12 stops). This needs a seat cap from you.
  - Shared fare split is still undefined.
  - Free cancels can be abused. I left this alone because you chose always-free.
  - ETA on a grid is thin: the shortest path is trivial, so only the traffic
    factors add anything.
  - Demand "prediction" is a moving average, not a real model.
  - Mutation checks are manual only, since no extra libraries are allowed.
  - Bigger phases: merging makes phases 2 and 4 heavier than your 2–3 minute
    review rule. I can split phase 4 into ride flow and payments if it runs
    long.

  - Phase 2: ranking weights.
  - Phase 3: fare rates, surge weights, time-of-day buckets, and how long offers

  The 2 phase 5 test edits, in simple words
  1. "Far rider gets refused" test. Rider A went 2 cells, rider B lived 9 cells
     away. Under my first rule the code could just finish A, then fetch B, so B
     was always accepted and the test failed. I changed it to trips where no
     stop order works for both riders. Now the test really checks that a bad
     pool gets refused. Stronger.
  2. "Planner skips a bad route" test. Same idea: the planner should skip the
     shortest route if it makes someone wait too long. The old example rejected
     every route under the new rule, so I picked new points where the shortest
     route (4) breaks the rule and the planner has to take a longer valid one
     (6). Same strength, new example.

  1. What I built
  - Pooled booking: request_ride(quote, pooled=True) now works end to end.
    - It first tries the nearest open pool with a free seat where the detour
      rule holds, and offers the ride to that pool's driver. Otherwise the first
      driver who accepts opens a new pool.
    - Pooled fare is 25% off.
    - The driver stays BUSY until the last pooled rider is dropped or cancels.
    - Cancel and reject remove only that one rider.
    - Pickup ETA follows the pool route.
  - Security fix: before, the customer passed in the driver count used for
    surge, so they could lower their own price. The engine now counts drivers
    itself through get_quote.
  - Duplicates removed:
    - one int check instead of 15 copies;
    - one star-rating check instead of 2;
    - one "is this the offered driver" check instead of 2;
    - remove now reuses leave instead of repeating it;
    - one shared test setup (tests/integration/world.py) instead of copying it.
  - Tests:
    - 6 pooled-flow tests.
    - 4 stress tests: 40 customers against 20 drivers, 14 riders racing for 2
      seats, 16 threads paying the same ride, and drivers moving while bookings
      happen. They passed 5 runs in a row. The concurrent-payment test also
      covers the gap I flagged in phase 4.
    - tools/mutate.py, the mutation check.
  - Mutation finding: one planted bug slipped through at first.
    test_every_transition reads its expected answers from the same table the
    code uses, so deleting "cancel mid-trip" from that table went unnoticed. I
    added a test that checks your rule directly, and now all 16 are caught.
  - README updated.

  2. Test count: 196 → 207.

  3. Assumptions I made without asking
  - Pools are matched nearest driver first. The 3-metric ranking is used only
    for solo rides and for a pooled rider's first driver.
  - Pooled trips don't count toward the driver speed factor, because detours
    would skew it.
  - When riders already in a pool are replanned (someone boards or leaves), the
    detour limit isn't re-checked, so a route always exists.

  4. Rules
  - Rule 4: one expected fare in a brand-new pool test was my own maths error (I
